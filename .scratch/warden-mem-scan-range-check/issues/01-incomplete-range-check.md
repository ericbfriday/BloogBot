# WardenMemScanHook uses incomplete range check, exposing patched bytes to Warden

Status: closed
Resolved-in: 2688559
Category: bug

> *This was generated by AI during triage.*

## Summary

`WardenMemScanHook` in `BloogBot/WardenDisabler.cs` uses an inline address range check that only tests whether a hack's **start address** falls within the scanned region. It does not check whether the scan covers the **tail** of a patch. This means a MemScan that starts partway through a patched instruction will read the modified bytes undetected.

## Affected file

`BloogBot/WardenDisabler.cs` — `WardenMemScanHook` (~line 433)

## Broken code

```csharp
var hacksWithinRange = HackManager.Hacks
    .Where(i => i.Address.ToInt32() <= IntPtr.Add(addr, size).ToInt32()
             && i.Address.ToInt32() >= addr.ToInt32());
```

This only passes a hack if `hack.Address` is within `[addr, addr+size]`. If the scan window starts at `hack.Address + 2` (covering bytes 2–5 of a 6-byte patch), the hack is excluded — Warden reads the patched bytes.

## Expected behaviour

The same `Hack.IsWithinScanRange()` helper used by `WardenPageScanHook` should be used here. It correctly handles both overlap cases:

```csharp
if (hackStart >= scanStart && hackStart < scanEnd) return true;  // start in range
if (hackEnd > scanStart && hackEnd <= scanEnd) return true;       // tail in range
```

## Fix

In `WardenMemScanHook`, replace:

```csharp
var hacksWithinRange = HackManager.Hacks
    .Where(i => i.Address.ToInt32() <= IntPtr.Add(addr, size).ToInt32()
             && i.Address.ToInt32() >= addr.ToInt32());
```

with:

```csharp
var hacksWithinRange = HackManager.Hacks.Where(h => h.IsWithinScanRange(addr, size));
```

`Hack.IsWithinScanRange(IntPtr scanStartAddress, int size)` already exists at `BloogBot/Hack.cs:24` and handles both start-in-range and tail-overlap cases correctly. No other changes needed.

## Impact

Warden MemScan scans a contiguous range of bytes at once (not byte-by-byte like PageScan). Any patch whose start address falls just before the scan window has its modified tail bytes exposed. This is a silent failure — no error is logged; Warden simply sees the patched bytes and may flag or crash the client.

## Agent Brief

**Category:** bug
**Summary:** `WardenMemScanHook` uses an incomplete range check that can expose patched bytes to Warden's memory scanner.

**Current behavior:**
When Warden's MemScan callback fires, the bot iterates `HackManager.Hacks` to find patches that fall within the scanned range, temporarily disables them, allows the read, then re-enables them. The range check used only tests whether a hack's *start address* falls within `[addr, addr+size]`. If a scan window begins partway through a multi-byte patch (e.g. scanning bytes 2–5 of a 6-byte JMP), the hack's start address is before the scan window so it fails the check — the patch is not disabled, and Warden reads the modified bytes directly.

**Desired behavior:**
Any hack whose bytes overlap the scan window — whether the overlap is at the start, the tail, or entirely contained within — must be disabled before the read and re-enabled after. This matches the behavior already implemented for the PageScan hook, which uses `Hack.IsWithinScanRange(address, size)`.

`Hack.IsWithinScanRange` handles all four overlap cases:
- hack start within scan window
- hack end within scan window
- hack entirely within scan window
- scan window entirely within hack

**Key interfaces:**
- `WardenMemScanHook(IntPtr addr, int size, IntPtr bufferStart)` — the method whose LINQ predicate needs updating
- `Hack.IsWithinScanRange(IntPtr scanStartAddress, int size) → bool` — the existing correct helper to use instead

**Acceptance criteria:**
- [ ] The LINQ predicate in `WardenMemScanHook` uses `Hack.IsWithinScanRange` rather than inline address arithmetic
- [ ] A hack whose start address is *before* the scan window but whose tail bytes *overlap* the window is included in `hacksWithinRange`
- [ ] A hack whose start address is *within* the scan window continues to be included (no regression)
- [ ] No other changes to `WardenMemScanHook` logic

**Out of scope:**
- Changing `Hack.IsWithinScanRange` itself
- Any changes to `WardenPageScanHook` (already correct)
- The broader WotLK Warden instability (separate issue)
